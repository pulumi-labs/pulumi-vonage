# Changelog

## [Unreleased]

## [0.3.1] - 2026-11-14

- Security: the Go SDK `go.mod` in the mirror now requires OpenTelemetry `sdk/log` v1.47.0 instead of v0.21.0, fixing GHSA-q7gw-24fr-5p69 (vulnerable >= 0.9.0, < 1.47.0) and clearing the pulumi-labs/pulumi-vonage Dependabot alert once released (fixes #1972). SDK generation change only. Not breaking.

### Security

- Security: updated OpenTelemetry (`go.opentelemetry.io/otel`, `sdk`, `trace`, `metric`, `log` and the OTLP trace exporters) from 1.45.0 to 1.47.0, which fixes GHSA-q7gw-24fr-5p69 (CVE-2026-128085, `AttributeValueLengthLimit` bypass in opentelemetry-go, vulnerable 1.33.0 to 1.46.x). Clears the pulumi-labs/pulumi-vonage Dependabot alerts for it once released (part of #1966). Not breaking.

### Fixed

- `pulumi destroy`, refresh and updates of an imported resource now use credentials and endpoints given only through environment variables (#1955, same root cause as #1951): after `pulumi import` the engine reconfigures the provider without running the config defaults (upstream pulumi/pulumi-go-provider#527), so the environment fallbacks were skipped; the provider config now fills unset settings from the environment in `Configure`. Not breaking.

## [0.3.0] - 2026-11-13

### Added

- `TenDlcReseller` resource (`companyName`, `phone`, `email`; registered with Vonage and The Campaign Registry, reviewed, `status` moves from PENDING to APPROVED or REJECTED) and the `getTenDlcReseller`, `getTenDlcResellers`, `getTenDlcEnums` (use cases and verticals typed, every other enumeration as IDs under `values`), `getTenDlcCampaignTermsAndConditions` and `getTenDlcThroughputs` lookups for the 10DLC API. Vonage has no call to update or delete a reseller: every input replaces it, destroy only forgets it (the reseller stays on the account), the registration is never retried, and a REJECTED reseller is kept in state with `rejectionReason` and reported as a partial creation. Import by reseller ID. Additive, not breaking. Mocked HTTP tests only; shapes from the 10DLC OpenAPI definition v1.0.34, not verified against a live account (fixes #1788, remainder in #1952).
- `TenDlcAccountSettings` and `TenDlcBrand` resources and the `getTenDlcAccountSettings`, `getTenDlcBrand` and `getTenDlcBrands` lookups for the 10DLC API (`/v1/10dlc`, US A2P messaging registration). `TenDlcAccountSettings` manages `optOutAssist`; it is a singleton (create adopts it, the ID and import ID is the account API key, destroy only forgets it). `TenDlcBrand` registers the business or person behind campaigns with The Campaign Registry: `entityType` is required and decides which other fields Vonage requires, the contact, tax ID and address fields are optional and unmanaged when unset, and `accountId` defaults to the provider `apiKey`. Most fields update in place (PATCH); `accountId`, `primaryAccountId`, `universalEin`, `altBusinessId`, `altBusinessIdType` and `verificationEmail` replace the brand. Registration is billed, so the create call is never retried after an unknown outcome. Destroy deletes the brand (Vonage then reports `DELETED` and answers 502 "Brand not found" on every other call, which reads as gone; Vonage refuses with 409 while the brand has campaigns). Import by brand ID. Outputs: `brandId`, `status`, `brandRelationship`, `campaignCount`, dates and ownership flags. Additive, not breaking. Mocked-HTTP tests only; shapes from the 10DLC OpenAPI definition v1.0.34, not verified against a live account. Campaigns and campaign numbers follow below (part of #1788).
- `TenDlcCampaign` and `TenDlcCampaignNumber` resources and the `getTenDlcCampaign`, `getTenDlcCampaigns`, `getTenDlcCampaignNumber` and `getTenDlcCampaignNumbers` lookups for the 10DLC API. `TenDlcCampaign` registers one messaging use case of a brand: `brandId`, `usecase`, `description`, exactly one of `messageFlowDetails` or the deprecated `messageFlow`, one to five `samples`, `helpMessage`, `optInMessage`, `optOutMessage` and `tcAgreed` (must be true) are required; keywords, `urlSamples`, `label`, reseller fields, `autoRenewal` and the content flags are optional and unmanaged when unset. Text fields update in place (PATCH); `usecase`, `vertical`, `subUsecases`, `ageGated`, `directLending`, `embeddedLink`, `embeddedPhone`, `hipaa`, `accountId` and `brandId` are locked by Vonage after approval and replace the campaign. The campaign is billed and reviewed (`status` moves from `PENDING_REVIEW` on its own) and the create call is never retried. Vonage cannot delete a campaign: destroy sets auto-renewal to false, and a campaign that has ended (terminated, canceled, expired, rejected) reads as gone. Import by `BRAND_ID/CAMPAIGN_ID` (`tcAgreed` is never returned and is set to true). `TenDlcCampaignNumber` links an owned number (`brandId`, `campaignId`, `country`, `number`); Vonage accepts the link asynchronously, so create reads it back and, when Vonage rejected it, reports a partial creation (the link stays in state so the next apply or destroy handles it instead of posting it again); every input replaces the link, destroy unlinks, import ID `BRAND_ID/CAMPAIGN_ID/NUMBER`. `messageFlowDetails` is Vonage's structured replacement for the deprecated free-text `messageFlow` (`consentMechanisms` with `method`, `details` and an `attachment` link that only `TEXT_TO_JOIN` may omit, `pricingDisclosure` (must be true), optional `carrierDisclaimer` (only true) and `brandName`, `frequency`, `privacyPolicy`, `termsAndConditions`); Check refuses setting both or neither, only the chosen field goes on the wire, `messageFlow` in the state is always the text Vonage holds (rendered from the details when those were used), and switching between the two updates the campaign in place. Additive, not breaking. Mocked-HTTP tests only; shapes from the 10DLC OpenAPI definition v1.0.34, not verified against a live account (part of #1788).

## [0.2.1] - 2026-11-11

### Fixed

- A resource input wired from another resource's output is no longer rejected at preview: the input checks of 15 resources (for example `Application`, `NumberPool`, `SubAccount`, `Number`, `NetworkApplicationProfile`, `VerifyTemplateFragment`) validated the zero value infer decodes an unknown to, so a program such as `applicationId: ${app.id}` failed with `must not be empty`. Check now skips the validation of values that are unknown at preview (also nested ones) and still validates the known ones; the apply-time Check is unchanged. Same bug class as namespace #1832.

## [0.2.0] - 2026-11-10

### Added

- `AccountSettings` resource and `getAccountSettings` lookup for the account's default SMS webhooks (`POST /account/settings`, the only endpoint Vonage offers). `AccountSettings` manages `moCallBackUrl` and `drCallBackUrl` and exposes `maxOutboundRequest`, `maxInboundRequest` and `maxCallsPerSecond` as read-only outputs. It is a singleton: create adopts the account's one settings record, the ID and import ID is the API key, a URL the program stops setting is cleared on the account, and destroy clears only the URLs it managed (the record itself cannot be removed; URLs it never managed are left alone). Vonage has no GET, so refresh and `getAccountSettings` send the POST with no fields, which the Vonage Node SDK documents as returning the current settings; this is not yet verified on a live account. Additive, not breaking. Mocked-HTTP tests only; shapes from the Vonage Node and Python SDKs (#1433).
- `NetworkApplicationProfile` and `NetworkApplicationProfileShare` resources and the `getNetworkApplicationProfile`, `getNetworkApplicationProfiles`, `getNetworkApplicationProfileShare` and `getNetworkApplicationProfileShares` lookups for the Network Registry API (`/v1/network-registry/application-profiles`). A profile registers an application (business profile, name, optional description, category, Network APIs with their purposes, infrastructure locations, optional privacy policy URL and terms acceptance) with the mobile operators. Vonage has no update call, so every input change replaces the profile (the new one is created first, the old one deleted; delete is soft, `delete_at` reads as gone). Optional inputs left unset are not managed and not sent; the Network API list and the locations compare as sets, and country codes ignore case. `status` and `statusMessage` are read back but never cause a diff. A share is created with `POST .../shared` (HTTP 202, asynchronous) and read by listing the accounts the profile is shared with; its ID is `PROFILE_ID/ACCOUNT_ID` and a share removed outside Pulumi reads as gone. Additive, not breaking. Mocked-HTTP tests only; shapes from the Network Registry OpenAPI v1.0.0 (`createApplicationProfile`, `getApplicationProfile`, `shareApplicationProfile`, `getAccountsApplicationProfileSharedWith`), not verified against a live account (#1433).
- `NetworkBusinessProfile` resource and the `getNetworkBusinessProfile`, `getNetworkBusinessProfiles`, `getNetworkRegistryCatalogue` and `getNetworkTermsAndConditions` lookups for the Network Registry API (`/v1/network-registry`). `NetworkBusinessProfile` registers a business with Vonage and the mobile operators (countries, contact, organisation type, tax number, privacy policy, postal address, optional vetting fields; import ID the profile ID). Registering is a legal submission that is reviewed, so `status` moves from `pending` on its own. Vonage has no plain update: a changed input is sent as a change request, which the profile takes over once approved; until then a refresh reports the requested values so there is no perpetual diff, and a rejected request is ignored so the next preview resubmits it. Destroy deletes the profile (a soft delete at Vonage; a soft-deleted profile reads as gone). Optional inputs left unset are not managed. `getNetworkRegistryCatalogue` reads every reference list (countries, organisation types, categories, CSPs, Network APIs, purposes, vetting levels with their extra fields, terms and conditions names), optionally filtered by `countries`. The API documents `https://api-eu.vonage.com` as its host: set `apiBaseUrl` (`VONAGE_API_BASE_URL`) to it if the default API host does not serve the path for your account. Additive, not breaking. Mocked-HTTP tests only; shapes come from the Network Registry OpenAPI definition v1.0.0, not verified against a live account. Application profiles and profile sharing are still to come (#1433).
- `MessengerAccount` and `ExternalAccountApplicationLink` resources and the `getExternalAccount`, `getExternalAccounts`, `getExternalAccountApplicationLink` and `getMessengerAccount` lookups for the beta External Accounts API (`/beta/chatapp-accounts`). `MessengerAccount` registers a Facebook Page (`externalId`, secret `accessToken`, optional `name`; import ID the Page ID; a token change is an in-place update, an ID change replaces). `ExternalAccountApplicationLink` links an application to a Messenger, Viber Service Message or WhatsApp account by `channel`, `externalId` and `applicationId` (one application per account; any change replaces; import ID `CHANNEL/EXTERNAL_ID/APPLICATION_ID`; destroy only unlinks and a missing link is quiet). The input is named `channel`, not `provider`, to stay clear of the resource option of that name. The `rcs` channel has no read endpoint in the spec, so it is only listable. `getMessengerAccount` returns the page access token as a secret; `getExternalAccounts` never lists it. Additive, not breaking. Mocked-HTTP tests only; shapes come from the External Accounts OpenAPI definition v0.1.6, not verified against a live account. An unset `name` is not managed (a name Vonage holds is left alone and is not a diff). Unverified: whether PATCH leaves the linked application alone (#1433).
- `User` resource and the `getUser` and `getUsers` lookups for the Vonage Users API (`/v1/users`), plus the JWT signer they need. `User` manages `name`, `displayName`, `imageUrl`, a free-form `customData` object and the `channels` a user can be reached on (`pstn`, `sip`, `vbc`, `websocket`, `sms`, `mms`, `whatsapp`, `viber`, `messenger`); the ID and import ID is the user ID (`USR-<uuid>`). A name left unset is generated by Vonage and is not a diff; changing an explicit name replaces the user. The Users API only accepts an application JWT, so these three need only `applicationId` and `privateKey` (RS256, PKCS#8 or PKCS#1 PEM, newlines flattened to a literal backslash-n accepted), a token is signed afresh for every request attempt, and they do not need `apiKey` and `apiSecret`; the other resources are unchanged and still use HTTP Basic. `getUser` finds a user by `userId` or exact `name`; `getUsers` lists every user (all pages) or the one matching `name`. Additive, not breaking. Mocked-HTTP tests only (the fake verifies the JWT signature); shapes come from the Vonage Python and Node SDKs, not verified against a live account. Unverified: whether PATCH merges or replaces (the provider always sends the full desired value of each field it manages and clears a removed one with null, `{}` or an empty list), and that PATCH cannot rename (so a name change replaces) (#1433).
- `getApplication` now returns the full capability tree: `voice`, `messages`, `rtc`, `verify`, `meetings`, `video`, `networkApis` and `vbc`, with the same shapes as the `Application` inputs and unset for a capability that is not enabled. Before, it returned only the list of capability names, so reading a webhook address or a region needed a second tool. The `capabilities` list is unchanged. Additive, not breaking. No secrets are in these blocks. Mocked-HTTP tests only (#1433).
- `NumberPool` and `NumberPoolNumber` resources and the `getNumberPool`, `getNumberPools`, `getNumberPoolNumber` and `getNumberPoolNumbers` lookups for the Number Pools API. `NumberPool` manages a pool's `fallback` (`Pool`, `CustomFrom`, `Reject`), `localizedSenderPreferred` and `predictableSenderPreferred` (import ID: the pool ID; changing `poolId` replaces it). `NumberPoolNumber` places one owned number in a pool (import ID `POOL_ID/NUMBER`; removing it only removes the number from the pool). Additive, not breaking. Mocked-HTTP tests only; shapes come from the Number Pools OpenAPI definition v2.0.4, not verified against a live account (#1433).
- `getPricing`: read-only lookup of Vonage's outbound price list for `sms`, `sms-transit` or `voice`, for one `country` (`GET /account/get-pricing/outbound/{type}`), a dialling `prefix` (`GET /account/get-prefix-pricing/outbound/{type}`) or every country (`GET /account/get-full-pricing/outbound/{type}`). Prices stay decimal strings in the account currency; a list shorter than the reported count is an error, not a partial answer. Additive, not breaking. Mocked-HTTP tests only; shapes come from the Vonage Node SDK `@vonage/pricing`, not verified against a live account (#1433).

### Fixed

- `pulumi import` of an object that does not exist (an ApiSecret, Application, Number, NumberPool, NumberPoolNumber, SubAccount, VerifyTemplate or VerifyTemplateFragment) now fails with an error instead of exiting 0 with an empty resource in state. Read returned the empty response that only a refresh treats as deleted. A refresh of a deleted object still drops it from state (#1715, same defect as #1712).

## [0.1.0] - 2026-11-04

### Added

- `VerifyTemplate` and `VerifyTemplateFragment` resources for Verify v2 templates and their per-channel, per-locale text (import IDs: the template ID, and `TEMPLATE_ID/FRAGMENT_ID`). Request shapes follow the Vonage Node SDK; Basic authentication on these endpoints is unverified against a live account.
- Lookup functions `getSubAccount`, `getApiSecret`, `getApiSecrets`, `getApplications`, `getVerifyTemplate` and `getVerifyTemplateFragment`, so every resource now has a lookup.
- `research/coverage/vonage.md`: the coverage inventory of the Vonage SDKs and APIs, with what is deferred and why.
- Lookup functions `getAccountBalance` (balance and auto-reload), `getNumbers` (owned numbers, filtered by country, pattern and application, following every page), `getAvailableNumbers` (numbers for sale in a country, one page, never buys) and `getSubAccounts` (all subaccounts, optionally by exact name). The response shapes come from the Vonage documentation and are unverified against a live account.
- `Application` accepts `video` (the fifteen Video API webhooks, each with `address` and `active`, plus `storage.serverSideEncryption`, `endToEndEncryption` and `cloudStorage`) and `networkApis` (`networkApplicationId`, `redirectUri`) capability inputs. A `video` or `networkApis` capability that is not declared is still preserved on update; removing a declared block disables the capability. Request shapes follow the Vonage .NET SDK (the Node and Python SDKs do not model these capabilities); unverified against a live account.

### Changed

- `go.mod`/`go.sum` moved from `provider/` to the provider's top level (the monorepo module path now ends in `lib/providers/vonage`); the Makefile builds from there. No change to the provider binary, schema or SDKs.

### Fixed

- BREAKING: `Number.acquisition` is create-only. Changing it no longer replaces the number (the replacement had the same ID, so the engine created it first and then deleted the old resource, which cancelled the number when `cancelOnDelete` was true). Edits are ignored after create and the state keeps the mode that was actually used. `country` and `msisdn` still replace.
- BREAKING: `Number` import IDs must be `COUNTRY:MSISDN`; an ID without the country is rejected instead of recording an empty country that forced a replacement on the next `up`.
- `Number` create now reports a failed or empty read-back after the purchase as a partial-state init failure (the number is tracked) instead of silently falling back to the inputs. An update that changes only `cancelOnDelete` no longer calls the Numbers API.
- BREAKING (behaviour): `ApiSecret` replacement at Vonage's two-secret limit: when the account already holds two secrets, changing `secret` now revokes the old managed secret before creating the new one, instead of always failing with 403. With one secret the create-then-revoke order is kept. The old secret stops working immediately and, if the new create then fails, consumers are left without a working secret; the choice is made in `Diff`, which lists the account's secrets, so a preview and the apply can disagree if the count changes in between.
- BREAKING: `ApiSecret` import IDs without `ACCOUNT/SECRET_ID` are rejected (previously accepted and sent to Vonage with an empty account).
- `Application` refresh no longer drops a declared `messages.version` (Vonage does not return it per its OpenAPI definition and SDK types; unverified against a live account), which showed a spurious update on every `up` after a refresh.
- `Application` refresh now reads back a declared `publicKey`, so a key rotated outside Pulumi is detected and restored. The comparison uses the decoded PEM, so line endings, wrapping and trailing whitespace are not drift. That the application PUT accepts `keys.public_key` is unverified against a live account (only the test fake demonstrates it).
- `Number` buy that ends in an ambiguous error (transport error, 5xx; the purchase is never replayed) now re-checks ownership: if the account owns the number the ID is tracked with an init-failed error instead of leaving a billed number untracked. Definitive refusals (4xx, Vonage error codes) are returned as plain errors.
- `Application` updates preserve capabilities the provider does not model (`video`, `network_apis`, ...) instead of stripping them with the full-replace PUT.
- BREAKING (behaviour): `SubAccount` now reconciles `suspended` and `usePrimaryAccountBalance` against the Vonage defaults: removing `suspended: true` from the program unsuspends the subaccount, drift is visible after refresh even when the program omits the field, and import adopts non-default values. `SubAccount.Update` now always sends explicit `usePrimaryAccountBalance` and `suspended` values (the effective values, defaulting to true and false), so a subaccount whose suspension or balance mode was changed outside Pulumi is reset to the program on the next update.
- Removed a dead import silencer, added tests for the non-replay of billed POSTs, pagination, partial-create paths, import and drift for every resource, and made the test fake follow the documented API (no `messages.version` or `voiceStatusCallback` in GET responses).
- Docs: README now describes create-only `acquisition`, import ID formats, the rotation behaviour at the secret limit, and that `voiceStatusCallback` cannot be refreshed.
- Provider config environment-variable fallbacks now work: `apiKey`, `apiSecret`, `applicationId`, `privateKey`, `apiBaseUrl` and `restBaseUrl` fall back to `VONAGE_API_KEY`, `VONAGE_API_SECRET`, `VONAGE_APPLICATION_ID`, `VONAGE_PRIVATE_KEY`, `VONAGE_API_BASE_URL` and `VONAGE_REST_BASE_URL` when the config keys are unset. The fallbacks were previously declared only as `env` struct tags, which the infer framework ignores.
- Security: updated the indirect dependency `github.com/klauspost/compress` from v1.18.7 to v1.20.2, which fixes GO-2026-6865 (GHSA-fpmh-frq8-7rj8, a panic on two-block frames). No behaviour changes.
- `getNumbers` and the ownership check behind the `Number` resource no longer stop paging when Vonage omits `count` from `/account/numbers`: a short page is the last page, a full page of 100 with no count is an error (previously the walk ended silently and could hide numbers on later pages, so a `Number` could conclude it was not owned). Exhausting the page cap in the ownership check is now an error instead of a "not owned" answer. Follow-up from the #1433 review.
- If the provider schema cannot be loaded during a `Read`, the failure is no longer cached for the life of the process: the next `Read` retries (#1599). The lookup functions were audited: none returns a credential value (`getApplication` returns the public key only), so no function output changes.
- Security: `pulumi import` and `pulumi refresh` now store the properties this provider marks secret (`ApiSecret.secret`, `SubAccount.secret`, `SubAccount.generatedSecret` and `Application.privateKey`) as secrets. A `Read` response only kept the secretness of the state it was given, and an import has no state, so a value the provider recovered from the API was written to the state as plaintext. The secret properties are read from the provider's own schema, so every resource is covered. State imported before this fix stays plaintext until its next `pulumi refresh`, which re-encrypts it (#1577).
- A preview no longer invents resource IDs. `Create` during `pulumi preview` returned the resource's logical name (or the placeholder `preview`) as its ID, so `id` was a known, wrong value and a program passing it to a lookup or to another resource ran against a name that does not exist and failed the preview (for example `getWebhook(webhook.id)`). A preview has no real ID now, so `id` stays unknown until the apply. Mirror issue https://github.com/pulumi-labs/pulumi-huggingface/issues/7 (#1590).
- Changing the provider configuration (a rotated token, API key or secret, a new endpoint or region) is an in-place update of the default provider. By default pulumi-go-provider replaced the provider on any config change, and replacing a provider replaces every resource that uses it, so rotating a credential would have deleted and recreated every resource. Each resource's own diff still decides whether it changes. Mirror issue https://github.com/pulumi-labs/pulumi-huggingface/issues/8 (#1591).

## 0.1.0

- Initial release: `Application`, `Number`, `SubAccount` and `ApiSecret` resources and `getApplication` and `getNumber` data sources for the Vonage account-management APIs.
- `SubAccount.secret` is create-only (the API cannot change it); later edits do not diff.
- `ApiSecret` replacement is decided by its `Diff` rather than schema-level `replaceOnChanges`, so importing an `ApiSecret` adopts the program's secret value in place instead of forcing a replacement (which would mint a new secret and revoke the old one). Changing the secret value or owning account of a managed secret replaces it; destroy treats an already-revoked secret as gone.
- `Number` voice routing is cleared on Vonage when removed from the program, and `voiceCallbackType/Value` and `voiceStatusCallback` are populated on refresh and import.
- The `apiBaseUrl` and `restBaseUrl` overrides must use `https` (loopback `http` is accepted for local fakes), since every request carries the account credentials as HTTP Basic auth.
- Docs: README notes the provider has not been validated against a live Vonage account.
